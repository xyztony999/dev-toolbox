# 架构重划报告 — 2026-11-11

触发：用户指令"重新划分本项目的领域架构"（/design 变更管理，BA 层发起） | 基线：9 个已交付模块的实现事实 + 旧根级三文档（v1.0，仅项目上下文域）

## 重划动机

1. 旧三文档是 2026-10-27 初始化初稿，只覆盖项目上下文一个域，与现状脱节。
2. 模块按**迁移批次**生长（runtime 三切片、toolchain-import、git-remote 分立），领域视角下需要聚合声明，避免后续功能继续按批次开平行模块。
3. session-launcher 交付后，"应用"主线成形，需要把它确立为核心域而非又一个平级模块。

## 新划分（BA v2.0 / AA v2.0 / FL v2.0）

- **L2 五阶段**（用户工作流）：认识项目 → 准备环境 → 连接协作 → 进入工作 → 保持健康。
- **L3 十一项关键业务**：按阶段归组，每项标注来源模块（见 BA §3）。
- **DDD 四层**：
  - 核心：项目上下文（internal/project）、环境应用与会话（internal/session）
  - 支撑：运行时管理（runtimecatalog/runtimeinstall/userstate）、Git 身份与仓库协作（gitidentity）
  - 基础数据：空缺（如实声明，不虚构字典类主数据）
  - 平台：桌面宿主与桥接（desktop）、遗留迁移工具集（各域 legacy 入口）

## 关键决策（AA §2）

| 决策 | 内容 | 影响 |
|---|---|---|
| 模块 ≠ 领域边界 | INDEX 模块是交付批次；代码归属按包结构（如 toolchain-import→runtimecatalog/external.go） | 新功能先定领域再选包，不再开平行模块 |
| 会话是唯一"应用"出口 | 所有资产经 EffectiveContext 求值进入会话；未来 ApplyPlan 落 session 域 | 防止应用逻辑散进支撑域 |
| userstate 双重角色 | 运行时域的资产清单 / 会话域的只读输入 | 保持 ADR-006 分离的应用层落点 |
| 基础数据域空缺 | 工具箱无共享主数据 | 显式空缺优于虚构 |

## 验证（SKILL Step 3/4）

- BA↔AA：11 项 L3 全部落入 4+2 个应用域，无孤儿；AA 无超出 BA 范围的业务模块（平台域除外，合规）。
- AA↔FL：导航三入口↔三域；FL 每个视图可追溯到 AA 功能模块。
- 与实现一致性：包映射逐一对齐 internal/ 现状；无前瞻性虚构能力。

## 待用户确认的归类裁量点

1. 目录绑定（includeIf）归入"连接协作"而非"身份档案"——语义是"目录↔身份的连接"。
2. 遗留迁移单列为平台工具集而非并入各域——便于后续 devswitch/gitid 迁移继续增长。
3. toolchain-import 不再作为独立领域（并入运行时管理域）。
